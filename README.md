# Engineering Playbook

这里长期维护三套工程规范。它们有相同的工程纪律，但处理的对象和完成证据不同：

| 规范 | 回答的问题 | 入口 |
|---|---|---|
| 开发 | 一个需求或缺陷怎样变成可交付的代码变化 | [开发规范](development/README.md) |
| 重构 | 怎样调整既有结构，同时保护或显式迁移行为 | [重构规范](refactoring/README.md) |
| 测试 | 怎样对一个精确版本建立可信的测试与发布结论 | [测试规范](testing/README.md) |

## 怎么使用

1. 根据当前任务只进入一套规范；不需要先读公共理论。
2. 先读该目录的 `README.md`，获得完整流程和最小清单。
3. 工作推进到哪个阶段，再打开对应的编号章节。
4. 需要落盘记录时，从 [`templates/`](templates/) 复制相应模板到业务项目。
5. 分支、环境、命令、设备和资源限制，以业务项目自己的规则为准。

开发中如果出现结构性改造，开发规范仍负责需求和交付边界，重构规范负责该部分的行为保护与迁移；测试规范则独立判断最终精确版本是否通过。

## 共同底线

三套规范都直接写明并遵守以下规则：

- 结论必须绑定精确基线、版本或产物；
- 流程重量与风险匹配，拿不准时按较高档准备；
- 实际工作偏离已确认范围时先停下、记录并裁决；
- 机械检查负责事实，独立复核负责语义判断；
- 修订、评审和复测保留历史，不覆盖旧结论；
- 用户负责业务取舍、风险接受和最终放行，不重复技术体力活；
- 交接依赖落盘文档、commit、diff 和原始证据，不依赖聊天记忆。

## 资产边界

- 本 Git 仓库是三套规范和模板的唯一可编辑源，不与 Notion 双写。
- 本仓不保存真实任务的 `cases/`；需求、方案、评审和测试记录留在业务项目。
- 本仓不写具体项目的地址、分支名、SDK 路径、账号或共享设备规则。
- 项目可以采用某个 Playbook 版本，并在自己的 `AGENTS.md` 或等效文件中补充落地规则。

## 目录

```text

refactoring/      重构规范，按基线到收口的顺序阅读
testing/          测试规范，按准入到发布结论的顺序阅读
templates/        需要复制到业务项目的记录骨架
MAINTENANCE.md    三份规范如何保持一致
SOURCES.md        初始迁移来源与基线
CHANGELOG.md      版本变化
VERSION           当前版本
```
