# 4. 测试通过、业务验收与发布准入

[← 上一章：缺陷与复测](03-defect-and-retest.md) · [测试规范](README.md)

## Gate T1：独立测试通过

只有同时满足以下条件，测试职责才能对当前精确版本给出“已通过”：

- 全部必测项通过；
- 阻塞清零；
- 未执行项不属于规定范围，或已经得到明确裁决；
- 证据能够对应当前版本、产物、环境和平台；
- 没有未覆盖的新版本变化；
- 失败修复已经完成复测和相关回归；
- 剩余风险和盲区已经完整说明。

开发者自己的测试只能作为开发自测，不能替代独立 Gate T1。

## Gate T2：业务验收

向用户提供 Gate 卡片：

- 本次验收的精确版本或产物；
- 已完成、失败、阻塞和未执行统计；
- 主路径、高风险路径和回归结论；
- 需要用户决定的业务取舍或风险；
- 1–3 个可选抽查入口；
- 最大剩余风险；
- 通过和不通过后的动作。

用户判断业务结果和剩余风险是否可以接受。没有明确确认时，状态保持“待业务验收”。技术事实由测试职责建立，用户不需要重复执行全部机械检查。

## 发布准入

至少满足以下条件，才能记录为“可发布”：

- Gate T1 和 Gate T2 都已通过；
- 最高优先级缺陷清零，其他遗留风险已经明确接受；
- 测试记录绑定当前候选版本，没有未覆盖的新变化；
- 高风险功能完成有效数据的端到端和结果核对；
- 业务项目自己的合并、审批和发布规则已经满足。

“已推送供测试”“测试包可安装”“合并请求已创建”都不等于可发布。通用规范不规定应直接推送还是创建 MR，也不规定具体集成或发布分支。

## 集成后验证与归档

集成后执行业务项目规定的最小冒烟，确认实际集成对象仍是已验收版本。失败时停止发布，固定新版本和证据，回到缺陷修复与复测流程。

归档内容包括：测试计划、精确版本与产物、运行环境、用例结果、原始证据索引、缺陷与复测轮次、Gate 决策和遗留风险。历史记录按当时采用的 Playbook 版本解释，不追溯覆盖。
